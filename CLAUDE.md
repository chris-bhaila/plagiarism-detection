# CLAUDE.md

Notes for working on this codebase — kept here (not in chat-only memory) so they're available from any machine this repo is cloned on.

## UI conventions

- **Page container width is set once**, in `resources/views/layouts/app.blade.php` (`$containerClass`, driven by `App\View\Components\AppLayout::$maxWidth`). Individual page views must NOT wrap their own content in a `max-w-[...] mx-auto px-8` div — that caused widths to drift inconsistently across pages. Instead:
  - `<x-app-layout>` — default, 1360px. Listing/dashboard pages.
  - `<x-app-layout max-width="narrow">` — 640px. Single-column edit/create forms (e.g. `admin/users/edit`, `admin/courses/create`).
  - `<x-app-layout max-width="form">` — 760px. Longer-form single-column pages (e.g. `student/assignments/submit`).
  - The top nav bar (`layouts/navigation.blade.php`) intentionally stays at a fixed 1360px regardless of page width — it's page chrome, not page content.

## Domain model (faculty / semester / course)

- `Faculty` `hasMany` `Semester` — every faculty always has exactly 8 semesters, auto-created together when the faculty is created (`AdminFacultyController::store()`). There's no UI to add/remove individual semesters.
- `Semester` `belongsTo` `Faculty`. Both `Course` (`semester_id`) and `User` (`semester_id`, students only — null for teachers/admins) belong to a semester.
- **Enrollment is fully automatic, not a pivot table**: a course's roster is every student sharing its `semester_id`. `Course::students()` and `User::enrolledCourses()` (a `hasManyThrough`) compute this on the fly — there is no `course_user` table.
- Only admins manage the structure: creating faculties, creating courses (picking a semester and, optionally, a teacher). Teachers get read-only course/roster views; they cannot create courses or manually enroll students.
- `courses.teacher_id` is **nullable** — a course can exist "Unassigned" and be given a teacher later via `admin.courses.edit`/`update`. Anywhere `$course->teacher` is displayed, null-check it (views show an "Unassigned" badge). Any collection of `teacher_id`s being deduped for a count/list must `->filter()` out nulls first.
- Admin pages: `/admin/faculties` (card grid) → `/admin/faculties/{faculty}` (semester cards) → `/admin/semesters/{semester}` (courses, teachers, students for that semester, plus the "add course" form) → `/admin/courses/{course}` (full detail: roster + assignments, plus an "add assignment" form) → `/admin/assignments/{assignment}/submissions` → `/admin/similarity-reports/{report}` (with confirm/review/dismiss actions). `/admin/courses/{course}/edit` (rename/move/reassign teacher) hangs off the same course.
- **Admin has full parity with a course's teacher** for assignments/submissions/similarity-reports: `AdminAssignmentController`/`AdminSimilarityReportController` intentionally *duplicate* (not share) the logic in the teacher-only `AssignmentController`/`SimilarityReportController` — same scoring/filtering, same create-assignment validation, same status-update (`confirmed`/`reviewed`/`dismissed`). If that logic changes in one pair, update the other — there's no shared service layer between them by design (keeps the two permission levels' routes/controllers independently readable), so it's easy to let them drift if you only touch one side.
- The teacher-side "create assignment" form (`teacher/assignments/index.blade.php`) didn't exist until this was built — the route/controller (`AssignmentController::store`) had been unreachable from the UI. Fixed alongside the admin version so both are usable.
- **Assignment attachments**: an assignment can optionally carry one uploaded file (`.docx` only, 10MB cap — see the `mimes:docx` rule in both `AssignmentController::store` and `AdminAssignmentController::store`). Stored on the **private** `local` disk (`storage/app/private`, not the public one) under `assignment-attachments/`, via the shared `App\Http\Controllers\Concerns\StoresAssignmentAttachment` trait — this bit *is* shared between the teacher/admin controller pair since it's pure storage plumbing, not permission logic (unlike everything else in that pair, see above). Served through one shared authenticated route, `assignments.attachment` → `AssignmentAttachmentController::download`, which self-checks the requester: admin always allowed, a teacher only for their own course, a student only if enrolled (same `semester_id` as the course). Don't switch this to the public disk / a raw `Storage::url()` link — that would bypass the enrollment/ownership check entirely.
- **Admin student profile** (`/admin/users/{user}` → `admin.users.show`, `AdminUserController::show`): a read-only page (not the narrow account-edit form) showing a student's faculty/semester, their auto-enrolled courses, and every assignment across those courses with this student's own submission status — "Not submitted" badge, or submitted-at plus the similarity report's review status if one exists. `abort_unless($user->isStudent(), 404)` — teachers/admins don't have this page (they have no faculty/semester/courses in the same sense). Linked from the student's name in `admin/users/students.blade.php` (the row's "Edit" button still goes to the account-edit form separately).
- **Admin account creation** (`/admin/users/create` → `admin.users.create`/`store`, `AdminUserController::create`/`store`): admin can create new **student or teacher** accounts through the UI (name/email/password/role, plus faculty→semester picker when role=student — same cascading-select pattern as registration/edit). **Deliberately does not offer admin as a role choice** — `Rule::in([ROLE_STUDENT, ROLE_TEACHER])`, no `ROLE_ADMIN` — that's a explicit product decision (new admin accounts are provisioned directly against the database, not through the app). The existing role dropdown on `admin.users.edit` still allows promoting an *existing* account up to admin — creation and role-switching are different concerns, and only creation excludes admin.
- **Admin teacher profile** (`admin.users.show` when `$user->isTeacher()` → `admin/users/show-teacher.blade.php`, a distinct view from the student one at the same route): courses taught, each row showing student/assignment/pending-review counts (pending-review computed by joining `SimilarityReport` → `Submission` → `assignment_id` across that course's assignments — an N+1-per-course query, acceptable at this app's scale). `AdminUserController::show()` now branches on role: `abort_unless($user->isStudent() || $user->isTeacher(), 404)` — still 404s for admin accounts, there's nothing to show them.
- **Teacher search**: `admin.teachers` now takes a `?search=` query param (name/email, `UserRepository::teachers(?string $search)`) — the students list already had faculty/semester filters, teachers had nothing until now.
- **Faculty rename**: `PATCH admin.faculties.update` — inline rename on the faculty show page (click "Rename" → text input replaces the `<h1>` via Alpine `x-show`). Semesters stay fixed regardless (no rename/add/remove for those, by design).
- **Course and assignment delete**: `DELETE admin.courses.destroy` (admin-only, cascades to the course's assignments → submissions → similarity reports) and `DELETE admin.assignments.destroy` / `DELETE assignments.destroy` (admin and the owning teacher respectively — assignment delete has the same teacher/admin-parity duplication as create, see above). All three confirm via a plain `onsubmit="return confirm(...)"` before submitting, since the cascade is irreversible. Deleting an assignment also removes its attachment file from disk (`Storage::delete($assignment->attachment_path)`) before the DB row goes, so orphaned files don't pile up in `storage/app/private/assignment-attachments/`.
- **Assignment editing**: `admin.assignments.edit`/`update` and `assignments.edit`/`update` (teacher, ownership-checked same as destroy). Editing reuses the create form's fields plus attachment handling via `StoresAssignmentAttachment::replaceAssignmentAttachment()` — uploading a new file deletes the old one and swaps in the new; checking "Remove" (with no new file) clears both DB columns and deletes the file; leaving both alone keeps the existing attachment untouched. This is the third method added to that trait alongside `storeAssignmentAttachment()` — still shared plumbing, not permission logic.
- **Course codes are globally unique** (`Rule::unique('courses')` in both `AdminCourseController::store` and `::update`, `->ignore($course->id)` on update). This was a gap from when course creation moved from teacher-scoped (`Rule::unique('courses')->where('teacher_id', ...)`, back when teachers created their own courses) to admin-only/global — the per-teacher scoping got dropped along with the rest of that flow and nothing replaced it until now.
- **`similarity_threshold` gotcha**: the DB column is `NOT NULL DEFAULT 0.35`, and the validation rule is `nullable` (so admins/teachers can leave it blank). Those two don't compose safely on their own — a blank number input still submits as an *empty string*, which the `nullable` rule turns into `null`, and Eloquent then inserts that literal `null` into a NOT NULL column, not "fall through to the DB default" (the column is explicitly listed in the INSERT once it's a key in the array, default only applies when the column is omitted from the INSERT entirely). Fix: both `AssignmentController` and `AdminAssignmentController`'s `store()` explicitly fall back to `Assignment::DEFAULT_SIMILARITY_THRESHOLD` (0.35, matching the migration) when the validated value is null; their `update()` methods fall back to `$assignment->similarity_threshold` (the existing value) instead, so clearing the field on an edit doesn't silently wipe out a previously-set custom threshold. **Any other nullable numeric/enum column with a non-null DB default needs the same explicit-fallback treatment in its controller** — `due_date` and `description` are fine because those columns are genuinely nullable in the DB, not defaulted.

## Teacher-side student detail

- `courses.students.show` (`GET /courses/{course}/students/{student}` → `CourseController::showStudent`) mirrors the admin student profile, but scoped to one course: every assignment in that course, this student's submission (if any) with its similarity review status, "Not submitted" badge otherwise. Linked from the roster row in `teacher/courses/show.blade.php` (previously plain text, no link).
- Two authorization checks, in order: `authorizeTeacherOwnsCourse` (the usual 403 if the course isn't theirs), then `abort_unless($student->isStudent() && $student->semester_id === $course->semester_id, 404)` — a 404, not 403, for a student who exists but isn't actually in this course's semester (matches how the rest of the app treats "not in scope" vs "not allowed").
- Deliberately course-scoped rather than "this student across every course I teach" — simpler to reason about and matches the click-through entry point (a specific course's roster). If a teacher teaches the same student in two different courses, they'd see two separate (correct, non-overlapping) views, one per course.

## Teacher course page consolidation

- **`courses.assignments.index` no longer exists** — teacher assignments used to live on their own page (`teacher/assignments/index.blade.php`), a click away from the course's roster (`courses.show`). They're now combined on `courses.show` itself (same two-column layout as `admin.courses.show`: assignments + create-assignment form on the left, roster on the right), matching what admin already had for the same course. `AssignmentController::forCourse()` is gone; `CourseController::show()` now loads both `roster` and `assignments`. Every redirect that used to target `courses.assignments.index` (`AssignmentController::store`/`update`/`destroy`) now targets `courses.show`.
- **Search**: `courses.index` (teacher's course list) takes `?search=` (name/code — `CourseRepository::forTeacher(User $teacher, ?string $search)`), same pattern as `admin.teachers`. The roster on `courses.show` has a **client-side** Alpine filter instead (only rendered once the roster exceeds 5 students) — no server round-trip needed for filtering an already-loaded, per-course list; each row's `x-show` matches against a `@js()`-escaped lowercase `"name email"` string built server-side.

## Bulk similarity-report review & CSV export

- **Bulk status update**: `similarity-reports.bulk-update-status` (teacher) / `admin.similarity-reports.bulk-update-status` (admin), both `PATCH`, registered *before* the `{similarityReport}` show route in each group (same HTTP verb doesn't collide with the `GET` show route, but keep the static path first regardless — habit worth keeping if a same-verb static route is ever added here). Checkboxes on the submissions page (`teacher/assignments/submissions.blade.php` / `admin/assignments/submissions.blade.php`) bind to an Alpine `selected` array; a hidden `<form id="bulk-status-form">` outside the visible table holds `report_ids[]` as `x-for`-rendered hidden inputs, and the three action buttons (Confirm/Reviewed/Dismiss) are `type="submit" form="bulk-status-form" name="status" value="..."` — clicking one submits that form with its own status value, no JS-driven form assembly needed. The teacher endpoint checks *every* selected report's course ownership before updating any of them (`abort_if` inside a loop) — an all-or-nothing batch, not partial-apply-then-fail.
- **CSV export**: `assignments.submissions.export` / `admin.assignments.submissions.export` — streams a CSV of every submission's score/status for an assignment (via `response()->streamDownload()`), always the *full* set regardless of whatever filter (`flagged`/`pending`/`cleared`) is active on the page. Both the submissions-review page and the export reuse the same row-building logic, factored into `App\Http\Controllers\Concerns\BuildsSubmissionRows` — like `StoresAssignmentAttachment`, this is shared between the teacher/admin controller pair because it's pure scoring/shaping logic, not permission logic (the intentional-duplication policy above only applies to permission-relevant code).

## Submission follow-up notes

- New `submission_notes` table (`SubmissionNote` model: `submission_id`, `author_id`, `body`) — a running, timestamped log of notes a teacher/admin leaves on one student's submission (e.g. "please revise your citations"). `Submission::notes()` is `hasMany(SubmissionNote::class)->latest('id')` — **order by `id`, not `created_at`**: two notes added within the same second (common in a test, or a teacher adding several quickly) tie on the second-precision `created_at` column and sort unpredictably; `id` is the only reliable insertion-order tiebreak. Learned this the hard way — the first version of this feature's test failed intermittently on exactly that tie.
- **Authored by teacher/admin only; students get a read-only view** on their receipt page (`student/assignments/submit.blade.php`, "Feedback from your instructor") and a note count on the student dashboard. There's no student-facing route to *create* a note. (This bullet used to say no student surface existed — that went stale once the student assignment-review work landed.)
- UI: an expandable "Notes (N)" toggle per row on the submissions-review page (`teacher/assignments/submissions.blade.php` / `admin/assignments/submissions.blade.php`), independent of whether the submission has a similarity match — unlike "Report" (only shown when `$row->topReport` exists), every submission gets a Notes toggle since a follow-up note isn't tied to a similarity flag. Each row needed its own `x-data="{ notesOpen: false }"` scope wrapping *both* the grid row and the conditional panel below it — the panel isn't inside the grid (would break the column layout), so the row markup changed from a single grid `<div>` to an outer non-grid wrapper containing the grid row plus a sibling notes panel.
- Routes: `submissions.notes.store` / `admin.submissions.notes.store`, both `POST`. Teacher endpoint (`SubmissionNoteController`) checks `$submission->assignment->course->teacher_id` ownership; admin (`AdminSubmissionNoteController`) doesn't, per the usual parity pattern.
- **Also addable from the similarity-report page** (`teacher/similarity-reports/show.blade.php` / `admin/...`), not just the submissions list — since a report always involves *two* submissions (from two different students), notes there are per-submission-side: each "Source A"/"Source B" card gets its own independent Notes toggle + thread, submitting to that specific submission's `notes.store` route. There's no "note on the report" concept — only ever "note on submission A" or "note on submission B," reachable from either the submissions list or the report detail page for the same submission.

## Dashboard scoping

- `DashboardController::index()` (route `dashboard`, shared by teacher+admin middleware) is **scoped to the logged-in user's own courses when they're a teacher**, via `scopedCourseIds()` (`$user->coursesTaught()->pluck('id')` for a teacher, `null` for an admin — `null` means "no scoping, see everything"). Every query in the controller (`SimilarityReport`, `Submission`, `Assignment`, and `mostFlaggedAssignments()`) threads that `?array $courseIds` through a `->when($courseIds !== null, ...)` clause. This wasn't scoped at all originally — any teacher logging in saw flag rates and student data for *every course in the institution*, not just their own. If you add a new query to this controller, scope it the same way or the leak comes back.

## Real syllabus data

- `database/seeders/BcaSyllabusSeeder.php` seeds the actual BCA program syllabus (8 semesters, from itcollegenepal.com) as unassigned courses under the `BCA` faculty. It's idempotent (matches on `[semester_id, code]`) — safe to rerun via `php artisan db:seed --class=BcaSyllabusSeeder`. It's called from `DatabaseSeeder` after `DemoDataSeeder`.
- `DemoDataSeeder`'s placeholder/fake courses live under `BIM` on purpose, to avoid cluttering BCA's real syllabus data.
- Semesters VII and VIII each have 2 electives chosen out of a longer official list (the rest aren't in the seeder) — see the comment block in `BcaSyllabusSeeder` for the full elective option list if the choice needs to change.
- `database/seeders/DemoTeachersSeeder.php` (runs after `BcaSyllabusSeeder`) creates 10 demo teacher accounts — `firstname.lastname@ict.dev`, password `firstname123` — and assigns every course in the system (including all the previously-unassigned BCA syllabus ones) a random teacher from that set of 10. **Only the accounts are idempotent** (`updateOrCreate` by email); the course→teacher assignment step re-randomizes on every run, so rerunning `db:seed` reshuffles who teaches what — that's intentional, not a bug, but don't expect stable assignments across reseeds.
- `database/seeders/ChrisDemoSeeder.php` (runs **last**, after `DemoTeachersSeeder` — deliberately, so its own teacher assignment isn't clobbered by that seeder's random shuffle) gives `chris@teacher` an actual course to look at in the UI: takes over `CACS101` (BCA semester 1 — the same semester `chris@student` is already in, so they show up on the roster too), adds 5 more students there — same pattern as `DemoTeachersSeeder` but domain `@ics.dev` instead of `@ict.dev` (`firstname.lastname@ics.dev` / `firstname123`) — and 2 assignments with a deliberate mix of states (one student's submission flagged pending against another's near-duplicate text, one clean submission, two students who haven't submitted) so `courses.students.show` (the teacher-side student detail page) has something to actually show across all three states: not submitted, submitted, submitted-and-flagged. Idempotent (`updateOrCreate` throughout, keyed on natural identifiers — email, `[course_id, title]`, `[assignment_id, student_id]`, `[submission_a_id, submission_b_id]`).

## Student side

- **Home is the dashboard**: `User::homeRouteName()` returns `student.dashboard` (`GET /home`, `StudentDashboardController`) for students — counts (courses, submitted/total, overdue, instructor notes), a "needs attention" list (overdue first, then the next 5 unsubmitted by due date), and recent submissions. `ProfileController`'s post-profile-completion redirects still go to `assignments.index` on purpose.
- **Similarity status is release-gated everywhere a student can see it** (receipt page, prior attempts, dashboard's recent list): only once `Submission::isSimilarityReleased()`, via `SimilarityReport::studentFacingLabel()`; otherwise "In progress". If you add another student-facing surface showing check status, gate it the same way or unreleased flags leak. Students deliberately never see the full report (scores, matched passages) — only the coarse label.
- **Assignment list** (`assignments.index`) takes `?search=` (title / course name / course code) and `?status=` (`submitted`, `not_submitted`, `overdue`; unknown values ignored). Filtered in-memory on the already-loaded per-student collection in `StudentAssignmentController::index`, not in SQL.
- **Course list** (`student.courses.index`, `GET /my-courses`, `StudentCourseController`): the student's auto-enrolled courses with teacher (null-checked → "Unassigned" badge), submitted/total assignment counts and next unsubmitted due date; each row links to `assignments.index?search=<code>`. Read-only — no course detail page for students.
- All student routes sit under the student-only route group; the profile-complete gate is global `web` middleware (`EnsureStudentProfileComplete`), so new student routes get it for free.

## Teacher/admin workflow extras

- **Bulk release**: `assignments.similarity-release.bulk` / `admin.assignments.similarity-release.bulk` (`PATCH`, body `action=release|hide`), on `SubmissionSimilarityReleaseController::bulk` / `AdminSubmissionSimilarityReleaseController::bulk` (same teacher-ownership vs. no-check split as the per-submission toggle). "Release all"/"Hide all" links on the submissions page confirm first. Release only touches rows not yet released, so an earlier `similarity_released_at` isn't overwritten.
- **Submission text page**: `submissions.show` / `admin.submissions.show` (`SubmissionController`/`AdminSubmissionController`) — full submitted text (escaped, never `{!! !!}`), best match, release toggle, and the note thread. It's the only way to open a submission that has no similarity match. Both views are thin wrappers around `partials/submission-detail.blade.php` (`$prefix` = `''` or `'admin.'` picks the route family); linked from each row's "View" button.
- **Note thread partial**: `partials/note-thread.blade.php` renders the note list + add form for all four places notes appear (both submissions pages, both similarity-report pages, both submission text pages) — same `$prefix` convention. Don't re-inline note markup in a view; edit the partial.
- **Note edit/delete**: `submissions.notes.update`/`.destroy` (`PATCH`/`DELETE /submission-notes/{submissionNote}`) and `admin.` equivalents. Teacher: must own the course *and* be the note's author (an admin's note on their course is read-only to them, 403). Admin: any note, author unchanged. Edited notes show "edited" (`updated_at > created_at`, so an edit within the same second as creation won't show it).
- **Submissions page search/sort**: `?search=` (student name/email), `?sort=` (`score` default desc, `name`, `submitted` newest first, `words`), combined with the existing `?filter=`; tab links preserve them. The shaping lives in `BuildsSubmissionRows::searchAndSortRows()` (shared, like the row builder). The CSV export still ignores all of this and always exports everything.
- **Dashboard course filter**: `?course=<id>` on `dashboard`. The choices are `selectableCourses()` (a teacher's own courses; all courses for admin) — an id outside that list is ignored and falls back to the unfiltered scope, so it can't be used to peek at another teacher's data. Any new dashboard query must keep using `$courseIds`.
